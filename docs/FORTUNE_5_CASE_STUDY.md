# Fortune 5 case study: omnichannel order-core reconstruction

> **Status:** Synthetic composite architecture case. It is designed at Fortune 5 operating scale; it does not claim a deployment by, endorsement from, or access to any Fortune 5 company.

## Executive situation

A global retailer operates an order core assembled over twenty years: Java services, Python allocation jobs, store-edge scripts, schemas, workflow definitions, vendor adapters, and policy documents. The estate processes store, web, marketplace, pickup, delivery, and return flows. Hundreds of teams depend on behavior that is only partially documented.

The board-level risk is not “old code.” It is that no one can bind each replacement claim to the exact predecessor behavior, authority, verifier, consequence, and replay evidence. A conventional rewrite converts undocumented coupling into migration risk.

## The intervention

`ggen-create` is placed before `ggen-legacy` as the create-side compiler.

1. **Preserve:** point at an exact read-only predecessor tree.
2. **Fence:** refuse symlinks, escaped paths, unbounded trees, and implicit actuation.
3. **Observe:** hash and classify every admitted artifact.
4. **Construct:** emit a deterministic manifest, RDF model, and receiving contract.
5. **DO through BRCE:** manufacture the bundle only after explicit confirmation; emit a receipt over every output byte.
6. **Hand off:** `ggen` receives authority to manufacture candidate projections; `ggen-legacy` owns independent equivalence, replay, release, and sunset decisions.

## Operating model

The synthetic estate has six business-critical surfaces:

| Surface | Example obligation | Falsifier |
|---|---|---|
| Order acceptance | no acknowledged order disappears | accepted ID absent from durable event stream |
| Price authority | charged total matches admitted promotion/tax rules | mismatch against golden transaction corpus |
| Inventory allocation | no unit is allocated twice | duplicate reservation under concurrent replay |
| Store continuity | bounded offline operation and reconciliation | store cannot replay after network partition |
| Returns/refunds | refund and ledger remain exactly reconcilable | monetary or inventory imbalance |
| Audit/release | every actuation has identity and replay evidence | missing or invalid receipt chain |

`ggen-create` does not infer these obligations from source names. They enter as admitted authority and verifier inputs during the receiver-owned workstreams.

## Manufactured consequence

For an admitted predecessor SHA, `legacy.power` produces one content-addressed receiving bundle. Re-running against unchanged input is byte-stable and returns `changed=false`. Any predecessor drift causes replay to become `BUILD_BROKEN`. A foreign output directory is `REFUSED(LEGACY_OUTPUT_EXISTS_REFUSED)` unless the operator explicitly authorizes replacement.

The bundle makes parallel modernization lawful. Teams may construct candidate templates and verifiers for pricing, allocation, store continuity, or returns without granting any candidate ambient execution authority. One failed workstream remains topology, not total-program failure.

## Enterprise decision gates

| Gate | Required evidence | Initial state |
|---|---|---|
| Intake Admission | exact tree, bounded manifest, valid bundle receipt | `ALIVE` in the synthetic fixture |
| Solution Admission | ggen projection plus independent behavioral closure | `UNKNOWN` |
| Release Admission | operational, security, resilience, support, and rollback evidence | `UNKNOWN` |
| Sunset Admission | production equivalence window and customer authority | `UNKNOWN` |

## Economic effect

The program changes migration economics by turning repository archaeology into a reusable manufacturing input. Every new region, brand, channel, or acquired estate can reuse the same intake calculus while retaining its own exact subject identity and verifier set. The gain is not a speculative percentage. The defensible claim is structural: repeated manual reconstruction becomes deterministic, bounded, receipted manufacture.

## Board conclusion

`ggen-create` powers `ggen-legacy` by supplying what legacy programs usually lack: an exact admitted starting object and a deterministic receiving contract. `ggen-legacy` remains the independent receiver that determines whether the manufactured replacement has earned standing. The predecessor is never retired merely because generation succeeded.
